The main reason why the results for the KDD dataset differ so much from other datasets is how the data is structured and how it is processed. The KDD data is most likely sorted by class, for example long sequences of normal traffic followed by long sequences of a specific attack type such as Neptune, and then normal traffic again. Since the streaming loop (run_s4_stream) processes the test data sequentially using iloc[start:end] and does not shuffle it beforehand, the model often receives batches that contain only a single class. This leads to batches with only normal traffic or only attack traffic.

This directly affects the F1-score. When a batch contains no attacks at all (only label 0), the number of true positives must be zero, because there is nothing to detect. According to the F1 formula, this results in an F1-score of 0.0, even if the model correctly predicts all samples as normal. True negatives are not included in the F1 calculation, and with f1_score(..., zero_division=0) the score is explicitly set to zero in such cases. This is why batches containing only normal traffic produce sharp drops to zero in the F1 plot.

Additionally, the KDD dataset is known for the blocky nature of its attacks. Large-scale attacks such as DoS (e.g., Smurf or Neptune) appear in long, continuous blocks and are relatively easy to detect, often resulting in F1-scores close to 1.0 when such blocks are processed. When the stream switches back to normal traffic, the F1-score drops to 0.0 due to the previously described metric behavior. More difficult attacks, such as U2R, can cause genuine intermediate performance drops, but the dataset is dominated by massive DoS attacks, which makes these sharp oscillations especially visible in KDD compared to other datasets.
